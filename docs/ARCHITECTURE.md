# Architecture and upstream contract

The workbench is a companion to [Sebastian's SAST-Blackboard](https://github.com/U0iS112/654321). The Docker build checks out the configured `SAST_REF` commit into `/opt/sast` and installs the upstream pipeline dependencies listed in [`requirements-upstream-runtime.txt`](../requirements-upstream-runtime.txt). Compose publishes port 8031 on the host's loopback interface, keeps review data in a named volume, and runs with a read-only container filesystem. Updating Sebastian's source means selecting a newer reviewed commit and rebuilding the image.

The workbench calls the compatible `blackboard.codebase.core.blackboard_semantic_mapping.run_pipeline` in a child process. It supplies the upstream `datacorpus/vcslam` path, sample IDs, historical IDs, a workbench-owned output directory, and `run_evaluation=False`. The worker then imports the generated `*_mapping_results.json` files. This keeps mapping behavior in the external SAST repository while the workbench owns execution controls, display, and later review. An upstream change to the function signature or output format requires an adapter or worker update here.

## Proposed shared ontology dependency

The default image now pins fork commit `9f637920e9cf8e1ceaa63556105959a46d4d0ebc` on [`shared-ontology-context`](https://github.com/jundahuang9123/profile-requirements-extraction/tree/shared-ontology-context), based directly on Sebastian's original `074ddfc409bdd120c93a0b68773bafa464e56504`. This branch is a proposed upstream optimization; it has not been merged into Sebastian's repository. The pin uses a full commit SHA rather than a moving branch. `SAST_REPO` and `SAST_REF` remain configurable build arguments. Once a contribution is accepted, select its reviewed upstream commit and rebuild.

Pipeline and custom-data jobs default to **Shared context**, which places the ontology first for generation and documentation only. History, example-value and name signals, selection and councils retain their compact original task inputs. Council-triggered candidate regeneration still receives the ontology. **Legacy** selects the original prompt layout for comparisons. Mode is snapshotted in job metadata and results; the upstream `llm_context` export records the prompt version, ontology hashes, stage timing and reported cached-token counts. A missing cache metric is unknown, not a measured cache miss. No model warmup or extra inference is performed when choosing a mode. See [upstream design](https://github.com/jundahuang9123/profile-requirements-extraction/blob/9f637920e9cf8e1ceaa63556105959a46d4d0ebc/docs/SHARED_ONTOLOGY_CONTEXT.md).

The upstream revision, provider, model, JSON settings and context mode are execution conditions. Shared mode changes message order and namespace validation, so the original paper's accuracy cannot be assumed. The first seven-hour comparison found that adding the ontology to compact signals increased input processing while Qwen3.5 could not restore a recurrent checkpoint at the shared-prefix boundary. Prompt version `sast-shared-ontology-v2-compact-signals` removes those extra inputs. This is one behavioral correction with a version-label update for traceability; the model, adapter, validation and agent sequence remain unchanged. Offline tests exercise the corrected pipeline and UI contracts with mocked responses. The correction has no live timing or accuracy result yet; prefix equality alone does not establish cache reuse.

## Model connection boundary

**Model settings** stores provider, model, and endpoint profiles on the server. The four cloud providers use fixed official endpoints. Local profiles accept a private, localhost, or Docker-host address with a `/v1` path. Local model discovery lists the server's advertised model IDs; the connection test makes one short JSON inference request. Neither action starts or downloads a local model.

A newly entered key stays in server memory unless the user explicitly selects **Remember key on this Mac**. Remembered keys are written to `credentials.json` with mode `0600` in the data directory (the persistent Compose volume in Docker). This file is plaintext, not encrypted. Public settings responses contain availability/storage status, never key contents. Keys do not enter browser storage, saved job configuration, review events, or exported bundles. Environment credentials remain a fallback and are not copied to the credentials file unless entered explicitly. The remember checkbox can persist an existing session key, or move a remembered key back into session memory without re-entry. Logs and errors redact known keys; an already running worker necessarily holds its selected credential in process memory/environment.

Each job snapshots its provider, model, and endpoint. The secret is supplied only through the child worker's environment. Before importing upstream modules, the worker sets an upstream `OPENAIKEY` compatibility sentinel and installs a process-local facade for `openai.OpenAI`. The facade uses the real selected connection and keeps the original `chat.completions.create` response contract. The source checkout is external; the workbench does not patch or copy it into its application package. Provider/model/endpoint appear in job metadata and source context for provenance.

The facade maps `max_completion_tokens` to `max_tokens` for alternate providers and uses a default output limit of 4096 tokens when the upstream call supplies none. The short connection test requests 512 output tokens; bounded advisory review requests 1500. Cloud requests have a 90-second client timeout and local requests allow 900 seconds, with no automatic SDK retries, within the selected job time limit. Local jobs allow up to 7200 seconds; cloud jobs allow up to 1800 seconds. These controls do not reduce input context size. Model APIs have different capabilities, and prompt-based JSON can fail. Ollama uses an object-or-array JSON schema and rejects malformed JSON before it reaches upstream parsing; semantic validation remains upstream. Its optional thinking-off control sends reasoning_effort="none". Thinking and JSON-format settings are recorded in job and result provenance. These are changed execution conditions, not accuracy-equivalent replacements for an original run. A successful short connection test does not validate ontology-sized requests or every pipeline stage. Validation includes offline adapter tests, the Docker UI, and a complete sample `0044` pipeline run through local Ollama 0.35.1 with Qwen3.5 27B Q4_K_M, 65,536 context tokens and thinking off. The run completed in about 95 minutes and imported all four attributes and its original council discussion; the built-in evaluation was 0/4 exact reference matches before and after discussion. Cloud inference and other model configurations remain unverified.

## Results and review

`adapter.normalize` maps each SAST result into attribute items. IDs are derived from attribute names; candidate IDs are derived from validated mapping strings. Each item retains the original machine mapping, matrix, complete state, and logs. `runs.raw` stores imported machine output in full with a SHA-256 hash. Runs started by the workbench also include an added `workbench_context` field with source data and execution metadata; the original SAST fields are retained. Human review never updates `runs.raw`.

`Store` uses SQLite transactions. `items.version` starts at 1 and increments when a human decision is saved. `events` append posts, replies, agent responses, and decisions against an item version. `parent` identifies replies, and candidate IDs link posts to recorded validated candidates. Stale decisions return HTTP 409. Agent posts carry model and prompt metadata; they cannot change human decisions or machine output.

The **Original council record** is read from Sebastian's `discussions` export. The optional workbench **bounded agent review** is a separate two-role sequence that reads recorded context and posts advisory responses. It is not another execution of Sebastian's original council and cannot approve a mapping. Both remain distinguishable in the UI and exported review bundle.

The HTTP server accepts only localhost Host values for its published port and checks request Origin; mutations require a per-server token. Reviewer names are self-declared. The Compose port mapping restricts host access to `127.0.0.1:8031`. Saved runs, discussions, decisions, and job files stay in the local Compose volume. Configured model jobs send selected context to the provider; importing and inspecting existing runs does not.
